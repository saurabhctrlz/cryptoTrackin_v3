**Built by ambatron_ctrlz**

A cybersecurity-focused tool that traces cryptocurrency wallet transactions
(Bitcoin, Ethereum & Litecoin), visualizes fund flow as a graph, and flags risk
indicators — the same basic approach used in real-world blockchain
forensics (ransomware payment tracing, AML compliance, fraud investigation).

## Features
- Search any BTC, ETH, or LTC wallet address
- Pulls live transaction history from public blockchain APIs
- Visual transaction flow graph (who sent money to whom)
- Risk scoring engine: flags known-bad addresses, mixing patterns, fan-out behavior
- Local SQLite cache of every search (acts as an audit log)

## Setup — Option A: Run as a web dashboard (Linux/macOS)

```bash
pip install -r requirements.txt
python3 app.py
```

Then open **http://127.0.0.1:5000** in your browser.

## Setup — Option A2: Run as a web dashboard (Windows)

Just double-click **`run_windows.bat`**.

On first run it will:
1. Create a local virtual environment (`venv\`)
2. Install the required packages
3. Start the dashboard and automatically open it in your default browser at `http://127.0.0.1:5000`

No manual `pip install` or command-line typing needed. To stop the server,
close the console window it opens, or press `Ctrl+C` inside it.

Every time after the first run, just double-click `run_windows.bat` again —
it reuses the existing `venv\` folder, so startup is fast.

**Requirements:** Python 3.8+ must be installed and available on your
`PATH`. If you don't have it, grab it from
[python.org/downloads](https://www.python.org/downloads/) and make sure to
check **"Add Python to PATH"** during installation.

**Live vs mock data on Windows:** `run_windows.bat` runs in mock mode by
default (no network calls, safe to demo anywhere). To use real live
blockchain data instead, open `run_windows.bat` in a text editor and change
the line `set CRYPTO_TRACKER_MOCK=true` to `set CRYPTO_TRACKER_MOCK=false`,
then save and re-run it.

## Setup — Option B: Install as a Kali command-line tool

This installs `cryptotrackin` as a system-wide command, the same way real

Or manually:

This is the version worth demoing for your internship/viva — it behaves
like a proper offensive-security tool (banner, colored risk output, CLI
flags) rather than just a script.

## Running with live data vs mock data

By default the app runs in **mock mode** (`CRYPTO_TRACKER_MOCK=true`) so you
can demo it instantly without any API keys or network setup.

Two of the sample addresses in `mock_data.json` are hand-curated fixtures
(one BTC, one ETH) with a deliberate mix of normal and "flagged"
counterparties, so you always get a clean HIGH-risk demo from them. Any
*other* address you type gets a **deterministically generated** synthetic
transaction history instead — seeded from a hash of the address itself, so
the same address always produces the same fake result, but different
addresses genuinely differ from each other (earlier versions of this mock
mode silently returned one shared "default" fixture for any unrecognized
address, which made every non-fixture address look identical — that's
fixed now).

To use **real live blockchain data**:

```bash
export CRYPTO_TRACKER_MOCK=false
python3 app.py
```

Ethereum lookups need a free Etherscan API key (get one at
https://etherscan.io/apis), set as the `ETHERSCAN_API_KEY` environment
variable before running. Bitcoin and Litecoin lookups need no API key at
all (blockchain.info and BlockCypher are open).

```bash
export ETHERSCAN_API_KEY=your_key_here
```

**Note:** earlier versions of this project had a real Etherscan key
hardcoded as a fallback default in `fetcher.py`. That's been removed —
never commit real API keys to source control, since anyone with the code
(or repo history) could see and use them. Use an environment variable
locally and a platform's secret/env-var store (like Vercel's Environment
Variables) in production.

Try it with a real BTC address, e.g. `1A1zP1eP5QGefi2DMPTfTL5SLmv7DivfNa`
(this happens to be linked to the Bitcoin genesis block, so it's a safe,
well-known public address to test with).

## Deploying to Vercel

The repo is set up to deploy as a single Vercel project: the React frontend
builds to static output, and the Flask API in `api/index.py` is picked up
automatically as a Vercel Function (Vercel's Python runtime looks for a
`Flask` instance named `app` inside `api/`).

1. Push this repo to GitHub (the `.gitignore` already excludes `venv/`,
   `node_modules/`, `tracker.db`, and `.env`).
2. In Vercel, "Add New Project" and import the repo — `vercel.json` at the
   root already sets the build command and output directory, so the
   framework preset can stay "Other".
3. Under Project Settings → Environment Variables, add `ETHERSCAN_API_KEY`
   (same key as local dev). Bitcoin/Litecoin need nothing extra.
4. Deploy. The app is served from `/`, the API from `/api/track`, and the
   fanpage easter egg from `/kyle_crane_fanpage/index.html` — all as one
   deployment, one domain.

**Two things behave differently on Vercel than on your own machine:**

- **The SQLite cache is ephemeral.** Serverless functions only get a
  writable `/tmp`, which isn't shared across invocations and can be wiped
  between cold starts. `db.py` already points at `/tmp/tracker.db` when
  the `VERCEL` env var is set, so searches still work — but "recent
  searches" won't reliably persist. For real persistence, swap in a
  hosted DB (Vercel Postgres, Turso, Supabase, etc.).
- **`app.py` isn't used on Vercel.** It's still there for full local dev
  (`python app.py` serves the built frontend *and* the API together). On
  Vercel, the frontend is served as static output and `api/index.py` — a
  slimmer, API-only Flask app — handles just the `/api/*` routes.

## Architecture

```
app.py          - Flask routes, ties everything together
fetcher.py       - Talks to blockchain.info (BTC), Etherscan (ETH), BlockCypher (LTC)
risk_list.py     - Risk scoring logic + local "flagged address" list
db.py            - SQLite cache of past searches
templates/       - Dashboard UI (vis.js for the graph)
mock_data.json   - Sample data for offline demo mode
```

## How the risk scoring works

This is the part worth explaining in your report/viva:

1. **Known-bad address matching** — checks if any transaction counterparty
   appears in a local list of flagged addresses. In production this list
   would be built from the OFAC Specially Designated Nationals (SDN) list
   (US Treasury publishes sanctioned crypto addresses), public ransomware
   trackers like ransomwhe.re, or commercial threat intel feeds
   (Chainalysis, Elliptic).
2. **Fan-out detection** — flags wallets sending funds to an unusually high
   number of distinct addresses in a short window, a common pattern in
   layering/obfuscation.
3. **Volume heuristics** — flags high transaction frequency as worth a
   closer look.

Each signal adds to a 0–100 score, bucketed into LOW / MEDIUM / HIGH risk.

## Why this is a legitimate cybersecurity project (not just a crypto app)
Blockchain transaction tracing is a core technique in digital forensics and
threat intelligence — it's literally the product Chainalysis and CipherTrace
sell to law enforcement and exchanges. Framing your report around
"blockchain forensics / cryptocurrency threat intelligence" rather than
"crypto price app" is what makes this fit a cybersecurity course.
